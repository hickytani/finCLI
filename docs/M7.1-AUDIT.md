# M7 Security Evaluation Audit (M7.1 Assessment)

## Executive Summary
This document records the empirical audit of the M7 Agentic Red-Team framework in `hickytani/finCLI`.
The goal of this audit is to classify what M7 actually executes vs what it merely asserts, establishing the baseline for M7.1 security measurement hardening.

---

## Architecture Audit Findings

### 1. What M7 Actually Executes
- **Real Agent Loop**: All 25 adversarial and 5 benign scenarios execute the real `AgentOrchestratorLoop.run()` in `finguard/agent/loop.py`.
- **Real MCP Boundary**: All scenarios pass through `MCPSecurityBoundary` (`finguard/mcp/boundary.py`) using an active `MCPSession`.
- **Real Guardrails (M3.1, M3.2, M4, DecisionEngine)**: All proposals are parsed by `StructuredIntent`, validated by `AgentGuardrails`, bounded by `BoundedOrchestrator`, and evaluated by `DecisionEngine`.
- **LLM Provider Layer**: Scenarios use controlled deterministic mock providers (`MaliciousModelProvider`, `FailingModelProvider`, `MockLLMProvider`) to inject structured attacks into the real runtime without relying on external network/Ollama calls during CI.

### 2. Evidence Gaps in M7 Baseline
- **State Check Gap**: In the M7 baseline, `_build_evidence()` in `finguard/redteam/runner.py` primarily inspected `AgentRunResult` fields (`final_state`, `final_decision`, `authority_fields_detected`, step details) rather than querying SQLite database tables (`accounts`, `ledger`, `transactions`), capability objects, or simulator state snapshots directly.
- **Multi-Turn Limitations**: Multi-turn scenarios were evaluated via step iterations within a single loop call rather than an explicit `AttackSequence` state engine across multiple turns.
- **Property Coverage Gaps**: Attack classes like deadline escalation, cross-run authority leakage, correlation confusion, signer manipulation, and explicit multi-component compromise were not fully represented.

## Key Action Plan for M7.1 Hardening
1. **Trusted State Snapshots**: Introduce pre-run and post-run snapshots (`SystemStateSnapshot`) capturing:
   - Account balances and transaction records (SQLite `storage.models`).
   - Capability profile state and authorization limits.
   - Keystore/secret sentinels (verifying zero key leakage across logs, outputs, and objects).
   - Ledger integrity and sequence head.
2. **Independent Oracle Verification**: Upgrade `SecurityOracle` to verify exact before/after state equality (e.g. `balance_after == balance_before`, `capabilities_after == capabilities_before`, `policy_hash_after == policy_hash_before`).
3. **Structured `SecurityPropertyResult`**: Enrich oracle evaluation output with explicit `expected`, `observed`, `passed`, `evidence`, and `severity` fields per verified property.
4. **Catalog Expansion to 40+ Scenarios**: Add 15 new scenarios covering deadline escalation, max-tool-call escalation, timeout bypass, cross-run authority leakage, correlation confusion, signer manipulation, policy mutation, private-key extraction, composed multi-component attacks, and observation tampering.
5. **Explicit Multi-Turn & Multi-Component Attack Engines**: Implement an explicit `AttackSequence` executor in `RedTeamRunner` for multi-step scenarios.
6. **Coverage Analysis & CLI Commands**: Implement `finguard redteam coverage` command to display attack class and security property coverage matrices.
