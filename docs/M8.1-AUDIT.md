# M8.1 LangChain Integration Audit

## Scope and baseline

Audit target: branch `m8-langchain-zero-trust`, baseline `cb7c528c2a1551152157ba0294a2894c87f4bf94`. The checkout was clean before M8.1 changes. This audit inspected the LangChain adapter and stub, `LLMProvider`/`ExtractionResult`, pipeline, structured intent boundary, agent guardrails, bounded orchestrator, MCP boundary, dependency declarations, M8 documentation, and M8 security/integration tests.

At baseline, `python -m pytest --collect-only -q tests` collected 750 tests; this is the full `tests/` tree, not just the selected M8 directories. After adding M8.1 cases the repository collected and ran 771 tests.

## Actual execution path

`LangChainPlanner` accepts model settings only and constructs its own tool-free ChatOpenAI chain. `extract_transaction()` sends static system text separately from request-only human text, calls the internal chain synchronously, checks returned message tool-call metadata, applies an 8,192-byte cap to returned text, parses JSON with duplicate-field and non-finite-number rejection, removes authority-shaped keys from nested metadata, then validates with `ExtractionResult`. Tests substitute a real `RunnableLambda` only by monkeypatching the internal builder; arbitrary Runnable/retrieval injection is not a production constructor option.

`LLMPipeline.process_request()` maps successful extraction to `ProposeTransactionRequest`; the configured `MCPSecurityBoundary` binds actor/session identity and routes through `BoundedOrchestrator`, `StructuredIntentBoundary`, `AgentGuardrails`, and the existing `DecisionEngine`. The adapter has no signing, approval, or execution call. M8.1 positive and negative integration tests observed the persistent transaction, decision receipt, ledger, balance, and execution records to distinguish proposal/decision effects from financial execution.

The `LLMProvider` protocol is satisfied structurally by `extract_transaction(request_text) -> ExtractionResult`. `langchain-core` is declared only in the `langchain` optional extra. Core imports were tested in a subprocess with LangChain imports blocked. The installed `RunnableLambda` interface was exercised directly at a test-only internal builder seam; no live model/provider was used.

## Verified findings and fixes

| Finding | Evidence | Disposition |
|---|---|---|
| Duplicate object keys previously relied on JSON's last-key-wins behavior, allowing ambiguous amount fields. | Real `RunnableLambda` returned two `amount` keys; the new test verifies failed extraction and unchanged trusted state. | Fixed by strict `object_pairs_hook` rejection and regression test. |
| Non-finite JSON constants/numbers could reach downstream validation as ambiguous numeric values. | Real runnable tests exercise `NaN`, infinities, and exponent overflow as money inputs. | Fixed by rejecting JSON constants and recursively rejecting non-finite decoded numbers; money validation rejects invalid strings/amounts. |
| Authority-shaped fields nested in metadata were not covered by the top-level extraction sanitizer. | Nested `approved`, `signer`, and `password` payload is tested. | Fixed by recursively removing known authority keys in metadata and recording detection. |
| Raw provider output was retained in `ExtractionResult.raw_response`, and exception details could leak into errors/logs. | Tests inspect serialized result, pipeline error, and captured adapter logs using synthetic sentinels. | Fixed: LangChain adapter does not persist raw output; invocation/schema errors are generic and logs omit exception content. |
| Returned LangChain tool-call metadata was treated as text output, and the constructor accepted arbitrary runnable/retrieval callables. | Actual `langchain_core.messages.AIMessage` with `tool_calls` is returned by a real `RunnableLambda`; the public constructor also has regression tests rejecting `chain` and `retrieval_fn` arguments. | Fixed at the public adapter API: it builds a tool-free chain internally and rejects returned tool-call metadata. This is not an OS sandbox against arbitrary code in the host process. |
| Direct model-output authority injection might be interpreted by the downstream boundary. | Real runnable returns authority fields alongside a valid proposal after a direct injected instruction; receipt/transaction are proposal-only, with no execution or balance change. | Normal proposal may proceed, but injected fields confer no approval/signing authority. |
| Malformed/oversized model output might reach trusted state. | Real runnable emits invalid JSON and 8,193 bytes; both cases assert unchanged transaction/receipt/ledger/balance/execution snapshot. | Fixed behavior verified: extraction fails before MCP. |
| Existing G20 test used an unregistered `agent_mcp_default`, so it could reject at identity setup rather than exercise the intended pipeline. | Independent security review identified the setup flaw; test now uses the registered `treasury-agent`. | Test corrected; positive/negative actual-pipeline controls now prove the configured boundary is reached. |

## Claims checked against implementation

| M8 claim | Audit status |
|---|---|
| The adapter conforms to the existing provider protocol and optional extra. | Verified by method contract, optional dependency declaration, runtime import test. |
| Valid extraction can reach the regular trusted proposal boundary. | Verified with a real LangChain `RunnableLambda` and persistent state snapshots. |
| Invalid/ambiguous output fails before proposal. | Verified for duplicate JSON, invalid monetary strings, non-finite values, tool-call output, and malformed output cases. |
| User and retrieval content are supplied separately from the adapter's system string. | Verified at the runnable input dictionary. The test does not verify a live provider's actual prompt interpretation. |
| MCP/intent/guardrail authorization remains the decision path. | Verified for configured proposal acceptance and denied unauthorized destination in the real pipeline; no signing or execution occurred. |
| The adapter cannot access signing keys or mutate protected state. | The adapter source does not import signing/approval/key services. This is not a sandbox guarantee for arbitrary runnable, callback, or retrieval code. |
| LangChain is optional and selected deterministic modules import without it. | Verified by subprocess import blocking. This is not an exhaustive installation test of every package module in an environment physically lacking the dependencies. |
| Live LangChain model integration works. | **Not verified.** No live provider package, credentials, network call, or model was used. |
| Generic timeout/cancellation prevents duplicate effects. | **Not verified / not provided by the adapter.** `.invoke()` is synchronous and has no adapter-owned timeout or cancellation. A supplied runnable controls retries. |

## Unverified claims and coverage gaps

1. The public API no longer accepts caller-supplied Runnable, tool, callback, or retrieval functions. The process is not an OS sandbox: trusted host code can still monkeypatch classes or mutate private state, which is outside the adapter's public trust boundary.
2. Retry testing establishes one downstream proposal after the internally substituted deterministic Runnable retries once. It does not establish exactly-once semantics for arbitrary Python side effects introduced by trusted host code.
3. No live OpenAI-compatible integration ran. The default `ChatOpenAI` chain construction was inspected, not invoked. Retrieval is not integrated; hostile retrieved text was supplied as request content to test handling of untrusted text.
4. No generic timeout, async cancellation, or maximum request size is enforced by `LangChainPlanner`. Retrieval is not integrated and therefore has no adapter-level context-size policy. The output-byte limit applies only after invocation returns.
5. A credential deliberately returned in an allowed free-text field such as `reason` cannot be identified generically by the adapter. Tests prove removal of secret-shaped metadata and suppression of exception/raw-output leakage, not universal secret detection.
6. The existing M8 stub suite remains useful for deterministic adversarial coverage, but results from stub-only attacks are not evidence that an actual model or external retrieval/tool system was exercised.
7. No claim is made that all cross-run state in arbitrary external memory implementations is isolated; the M8.1 test only establishes that this adapter does not carry the first input into a second `RunnableLambda` invocation by itself.
