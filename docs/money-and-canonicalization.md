# Exact Money and Transaction Canonicalization

## Amount Contract

Money is authoritative as a positive integer number of minor units and an
explicit currency. `Money` is immutable; arithmetic and comparisons require
matching currencies and operate on integers. Transaction amounts are exposed
at external boundaries as decimal text, then converted to `Money` before policy
evaluation. New transaction creation does not accept floats or an
`amount_minor` argument separate from the currency-bearing value object.

| Input | Accepted form | Result |
| --- | --- | --- |
| USD `500`, `500.0`, `500.00` | ASCII decimal string or integer | 50000 minor units |
| USD `0.01` | ASCII decimal string | 1 minor unit |
| JPY `500` | ASCII decimal string or integer | 500 minor units |
| KWD `5.125` | ASCII decimal string | 5125 minor units |
| USD `0.001` | Rejected | Excess precision |
| Float, bool, NaN, Infinity, signed or exponent notation | Rejected | Invalid boundary input |

The configured exponent table supports INR/USD/EUR at 2 decimal places, JPY at
0, and KWD at 3. Unsupported currency identifiers are rejected; adding a
currency requires updating the enum and exponent table together. Amount strings
use ASCII digits, no signs, separators, surrounding whitespace, exponent
notation, or leading zeroes (except the value `0`, which is then rejected by
the positive transaction amount rule). Inputs longer than 64 characters and
values above `MAX_AMOUNT_MINOR` are rejected. YAML policy numbers that arrive
as floats are converted using their decimal string only and are accepted only
when exactly representable at the policy currency precision.

## Data Contracts

| Contract / field | Type and trust | Authoritative | Canonical / signed | Mutability and validation |
| --- | --- | --- | --- | --- |
| AI `amount` | string or integer from untrusted model output | No, until parsed | Not directly signed | `TransactionExtraction` validates against currency and `Money` |
| Transaction `amount` | immutable `Money` | Yes | v2 emits `amount_minor` and `currency` | Assignment is validated; new `canonical_version` is frozen to 2 |
| Decision receipt `amount`, `amount_minor`, `currency` | decimal string, integer, currency code | Receipt evidence derived from transaction | Receipt binds transaction hash; v2 field is recorded | Generated by `DecisionEngine` |
| Approval | stored transaction hash and approval payload | No independent amount | Bound to transaction hash | Approval service verifies the hash before signing |
| Signing payload | canonical transaction bytes | Yes, exact preimage | Ed25519 signs v2 bytes from `Transaction` | Signing gate reconstructs from stored `amount_minor` and rejects legacy rows |
| Actor authority limit | Decimal string plus `authority_currency` from signed identity data | Yes for the actor's spending limit | Control value is recorded in decision policy/receipt evidence | Decision, policy, risk, and signing block transaction currency mismatches |
| Transaction database row | `amount_minor` integer; `canonical_version` integer | New security decisions use these fields; Float `amount` is a Decimal-derived display shadow only | Canonical hash is stored | New decision writes set version 2; legacy rows default to v1 |
| Simulator account | `balance_minor` integer plus currency | Yes for synthetic settlement | Execution records bind transaction hash and signature | Conditional integer debit/credit; failures roll back |
| Simulator execution | integer transaction amount represented by signed hash | Derived from signed transaction | Hash/signature are checked again before movement | Exactly one execution row per transaction |

## Canonical Versions

Canonical v2 is:

```text
b"finguard.tx.v2\x00" + UTF-8(sorted-key compact JSON)
```

Its transaction object includes `canonical_version: 2`, `amount_minor`, and
`currency`. It contains no float amount. Signed transaction identifiers must
already be NFC and may not contain control or Unicode format characters.
Metadata is represented by the RFC 0001 digest already present in this branch.

Canonical v1 remains available only through an explicit version argument for
legacy verification. New transaction construction rejects v1, the signing gate
rejects stored versions other than 2, and the simulator refuses to execute
legacy rows. `tests/vectors/canonical_v1.json` freezes a v1 byte vector.

## Existing Database Limitation

The ORM retains the legacy `amount` Float column for old records and schema
compatibility. New inserts write a decimal-derived display shadow because
existing databases may retain `amount NOT NULL`; every authorization, hash,
approval, signing, search, risk aggregation, and execution path reads
`amount_minor` instead. Additive initialization columns default legacy rows to
v1. The dry-run/apply migration in `finguard.storage.money_migration` audits
the exact stored binary-float value, adds minor-unit/version/failure columns,
backs up before apply, quarantines inexact rows, and marks unsigned legacy
requests `FAILED/MIGRATED_REQUIRES_RESUBMIT`. Populated SQLite fixture tests
cover dry-run immutability, exact/inexact/non-finite examples, backup
requirement, quarantine, resubmit state, and idempotence. The tool has not been applied to
the operator database; backup restore and pre-v2 signed artifact verification
remain unverified. Do not run apply on valuable data without reviewing
dry-run output and preserving the required backup.

Account identities remain plain signed-registry source/destination strings;
there is no account registry, alias resolver, mixed-script defense, or
per-account currency enforcement yet. Actor authority and policy limit
currencies are explicit; decision, policy, risk and signing block mismatches.

This repository remains a synthetic financial simulator and security research
prototype, not a banking system.
