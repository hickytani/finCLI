# M8.2 — Bounded Execution & Failure-Safe Orchestration

**Branch:** `m8.2-bounded-execution`  
**Status:** Implementation complete — all 16 security test groups green  
**Core Invariant:**  
> An LLM may propose an intent, but it cannot extend its own execution budget, gain authority, bypass authorization, or cause duplicate financial effects through retries, timeouts, or late responses.

---

## 1. Design & Threat Model

FIN//GUARD treats all LLM providers and frameworks (including LangChain) as **untrusted data extractors**. Model output is a proposal only; deterministic security boundaries (MCP boundary, BoundedOrchestrator, StructuredIntentBoundary, AgentGuardrails, DecisionEngine, SigningGate) decide authority and financial state changes.

M8.2 hardens the LangChain integration (`LangChainPlanner`) and bounded orchestrator by enforcing:
1. **Input & output resource bounds** before expensive processing or parsing.
2. **Adapter-owned deadlines and provider request timeouts** with fail-closed semantics.
3. **Strict separation of static system instructions** from user-controlled prompt text and untrusted retrieved context.
4. **Idempotency and state consistency** across retries, cancellations, late responses, and concurrent duplicate requests.
5. **Stripping of budget/timeout override attempts** from model responses or metadata.

---

## 2. Resource & Time Bounds

The `LangChainPlanner` constructor accepts configurable, conservative defaults:

| Parameter | Default | Purpose | Failure behavior |
|---|---|---|---|
| `max_prompt_bytes` | `4 096` bytes | Bounds user request length | Fail closed (`extraction_success=False`) |
| `max_retrieved_context_bytes` | `8 192` bytes | Bounds untrusted retrieved context length | Fail closed (`extraction_success=False`) |
| `max_response_bytes` | `8 192` bytes | Bounds raw model output before JSON parsing | Fail closed before JSON parsing |
| `timeout` | `10.0` seconds | Wall-clock deadline for model extraction | Fail closed (`extraction_success=False`) |
| `max_retries` | `0` (max 3) | Bounded model invocation retries | Fail closed after retry exhaustion |

### Resource Limit Defense
- **Validation before processing:** Prompt and retrieved context lengths are validated *before* chain invocation. Oversized inputs are rejected immediately without invoking the model.
- **No silent truncation:** Financial instructions are never truncated in a way that alters meaning; oversized inputs fail closed.
- **Budget override protection:** Any attempt by model output, metadata, or retrieved text to supply budget/timeout keys (e.g. `max_steps`, `max_tool_calls`, `max_prompt_bytes`, `timeout`, `deadline`, `financial_limit`) is automatically detected as an authority field, stripped, and recorded in `authority_fields_detected`.

---

## 3. Timeout & Cancellation Semantics

1. **Deadline Enforcement:** `extract_transaction()` invokes the internal chain within a worker thread using `concurrent.futures.ThreadPoolExecutor(max_workers=1)`. If execution exceeds `timeout` seconds, a `TimeoutError` is caught and a fail-closed result is returned:
   `ExtractionResult(extraction_success=False, error_message="LangChain extraction timed out after X.X seconds.")`
2. **Caller Timeout vs. Underlying Thread Work:** Timing out the caller's wait cancels the caller's execution path and returns a fail-closed result. It does **not** guarantee that an OS thread or underlying HTTP network connection was forcefully killed by the OS.
3. **Late Response Containment:** If a timed-out worker thread completes after the caller timeout, its output is completely discarded. Late responses are never forwarded to `MCPSecurityBoundary` or `DecisionEngine` and produce zero transaction receipts or ledger entries.
4. **Exception & Secret Masking:** Exceptions raised during provider invocation or timeout do not leak raw exception strings, tracebacks, or secret sentinels into error messages, captured logs, or audit records.

---

## 4. Retry & Idempotency Behavior

1. **Bounded Extraction Retries:** `max_retries` defaults to `0` (bounded to at most 3). Model extraction is strictly non-authoritative proposal generation; retries during extraction perform 0 DB writes, 0 balance changes, and 0 signing calls.
2. **State Consistency:** Proposals reaching `MCPSecurityBoundary` flow through `StructuredIntentBoundary` and `DecisionEngine`.
3. **Duplicate Request Prevention:**
   - Repeated requests with identical parameters but different request IDs are evaluated safely as separate proposal attempts or rejected as `INTENT_ID_CONFLICT` if idempotency keys overlap with differing intent digests.
   - In all cases, `0` transactions are signed or executed (`0` balance changes, `0` execution records).

## 7. Verified Guarantees vs. Limitations

### Verified Guarantees
- Prompt, retrieved context, and model output size limits are strictly enforced before processing/parsing.
- Model extraction deadline is enforced with fail-closed handling.
- Late model outputs and retries do not produce duplicate financial execution effects.
- Model output and metadata cannot alter orchestrator or adapter limits.
- Zero financial transfers, zero balance changes, and zero signatures occur without explicit human approval outside the model.

### Explicit Limitations
- **Thread Cancellation:** Timing out the caller's wait cancels the caller's execution path and ignores late results, but does not forcefully kill an OS thread or underlying HTTP connection.
- **Live Model Testing:** Tests use deterministic `langchain-core` `RunnableLambda` / `AIMessage` interfaces offline. Live model requests require explicit credentials and are optional.
