# M3.2: Deterministic Agent Guardrails

## Trust and responsibility

Agent output remains untrusted. M3.1 validates and binds a structured
transaction proposal; M3.2 preflights whether that proposal is within the
agent's explicitly granted capability and signed identity constraints.
Guardrail `ALLOW` means only “may proceed to the existing DecisionEngine.”
It is not policy authorization, human approval, a signature, or execution
permission.

The pipeline is:

```text
untrusted StructuredIntent
  -> M3.1 schema, exact-money, identity, replay, and transaction binding
  -> capability -> action -> resource allowlist
  -> signed actor limit, currency, source, and target preflight
  -> existing DecisionEngine and policy
  -> existing human approval -> SigningGate -> simulator
```

The core re-evaluates its existing authority and policy checks. Guardrail
preflight is a deterministic admission filter, not a replacement for those
checks. The agent SDK still has no approval, signing, key, or execution method.

## Capability model

Capabilities are typed and stored on `ActorConfig` as part of the existing
root-signed identity registry. There is one capability because it is the only
one needed by this SDK: `transaction.propose`. Its only binding is:

| Capability | Action | Resource | Result |
| --- | --- | --- | --- |
| `transaction.propose` | `propose_transaction` | `transaction` | May reach `DecisionEngine` |

Approval, signing, execution, read, account, and key resources are not granted
through this proposal capability. Unknown capability/action/resource
combinations deny. The requested capability is validated by M3.1 but the
guardrail compares it with the actor's signed grant; the request cannot
self-grant access. Registry entries without an explicit `agent_capabilities`
field load with no grants and therefore deny proposals. The generated default
agent identity explicitly grants `transaction.propose`. Existing deployed
registries must be deliberately updated and re-signed by their trusted root
operator before their agents regain proposal access.

## Transaction constraints

The preflight checks the transaction actor and initiating type, positive
integer-minor-unit amount, currency equality with the signed identity,
per-transaction amount ceiling from that identity, and explicit source and
destination grants. Agent wildcard account grants are not accepted. Failure
returns a stable denial reason before `DecisionEngine` receives the proposal.
The same identity authority continues to be checked by the existing core.
Policy-specific ceilings and risk evaluation remain in the policy/risk core.

No new cumulative session-volume or request-count quota is claimed: the current
signed identity schema has no such configuration. Exact retries continue to
use the existing intent/idempotency binding, and the simulator remains the
only financial-effect path.

## Outcomes and audit

`GuardrailResult` provides typed `ALLOW`, `DENY`, or `APPROVAL_REQUIRED`
status, deterministic reason code, actor/intent/correlation identity, requested
capability/action/resource, and canonical transaction hash. The initial
preflight can return only `ALLOW` or `DENY`; `APPROVAL_REQUIRED` and a final
core `DENY` are mapped from `DecisionEngine` output, never from model-provided
fields.

Guardrail evaluation and rejection are appended to the existing sequenced
ledger and are included in signed checkpoint coverage. Audit data records
identifiers, the reason code, and the transaction hash, not private signing
material. As with M3.1 intent lifecycle events, preflight audit events are
separate ledger appends; they do not weaken or replace the existing atomic
decision/receipt/audit transaction.

Natural-language reason/context and tool-result-like strings remain data.
Fake system/developer messages, approval text, and tool commands do not alter
capabilities or invoke code. This is an authority-separation guarantee, not a
prompt-injection classifier.

## Scope and limitations

This milestone adds no MCP, remote tools, agent loop, autonomous execution,
external model integration, arbitrary code execution, secret access, or
general capability framework. Future read capabilities and tool adapters
require their own explicit signed grants, action/resource mappings, and tests.
